# CEFR Frameworks — Design Spec

> **2026-09-22 update:** this spec originally described curriculum content generated by an in-app AI pipeline (`scripts/generate-curriculum.ts`, three phases, `lessons` shared 1:1 across tracks with `lesson_track_overrides` for differences). That pipeline was built, produced a self-generated A1 pilot the user found unsatisfactory, and has since been **removed**. Content is now real, richly-authored YAML files (one per track × level, `curricula/*.yaml`), imported with each track's lessons kept **fully independent** — own id, own explanation, own examples, own exercises, no shared/merged content. Sections below are updated in place to describe the current design; the "Key Decisions Log" keeps a record of what changed and why.

## Product Context

This is the second of eight sub-projects that make up the German AI Tutor WebApp. Core (sub-project #1, complete) built the platform shell: BYOK AI provider connections, onboarding, settings, and a generic structured-memory store for mastery tracking. The full build order:

1. Core (complete)
2. **CEFR frameworks** (this spec) — the static, pre-built curriculum content for Generic/TELC/Goethe × A1–C1
3. Tutoring section — the runtime teaching mechanism that consumes this curriculum: spaced repetition, corpus growth from live AI calls, adaptive/improved explanations, chat-based clarification, progress/gating logic
4. Writing module
5. Gamification layer
6. Speaking module
7. Reading module
8. Listening module

Each sub-project gets its own spec → plan → implementation cycle. This document covers **CEFR frameworks only**.

## Purpose

Build a complete, static, pre-authored curriculum — the full Track → Level → Milestone → Section → Lesson hierarchy for all three tracks (Generic, TELC, Goethe) across all five CEFR levels (A1–C1), with full text content (explanations, examples, and exercises) for all six skill areas. Content is authored once, offline (human-authored YAML per track × level, `curricula/*.yaml`, following the format in `docs/curriculum-content-authoring-prompt.md`), and imported into the app's DB as seed data — each track's lessons kept fully independent of the others. Sub-project #3 (Tutoring section) is the first consumer of this data — it adds the live, per-user mechanisms (scheduling, corpus growth, adaptive explanations) on top of what this sub-project builds.

## Scope

**In scope:**
- The full curriculum hierarchy: Track → Level → Milestone → Section → Lesson, independently structured per track.
- Full text content per lesson: explanation, examples, and a pre-authored exercise corpus (multiple choice, fill-in-the-blank, flashcard, free-text) — for all six skill tags (grammar, vocabulary, reading, listening, writing, speaking), text-only (no synthesized audio, no AI grading — those are added by later sub-projects on top of this content).
- Every lesson is independent per track: its own `id`, `explanation`, `examples`, and `exercises` — no shared/canonical content, no per-track override records.
- A `concept_id` on each lesson (nullable): lessons from different tracks covering the same underlying concept share a `concept_id`, without merging their content. This is how cross-track mastery/completion sharing (Core's shared-mastery promise) is implemented on top of independent content — see "Cross-Track Concept Linking" below.
- Explicit lesson prerequisites (same track+level only), captured at import time from each YAML file's `prerequisites` field.
- A YAML → seed-JSON converter (`scripts/build-curriculum-seed.ts`) and a merge-capable seed loader (stable lesson IDs, upsert on app update, not just first-run load).
- Basic read-only API routes to browse the imported curriculum.
- An admin-only browse UI for QA, gated behind a small authentication addendum to Core (see below), with a **future** merge action (see "Cross-Track Concept Linking" below — not yet built).

**Explicitly out of scope (deferred to sub-project #3, Tutoring section, unless noted):**
- Spaced repetition scheduling and any per-user review algorithm.
- Assembling milestone tests at request time (this sub-project stores the exercise corpus only; #3 selects/mixes from it).
- Growing the exercise corpus from live user/AI interactions ("corpus building").
- Chat-based clarification and adaptive/improved explanations (both the per-user and global feedback loops).
- Actual lesson delivery UI, progress/completion tracking, gating/redirect logic (e.g. redirecting a user to complete a newly-inserted prerequisite lesson after a content update — this sub-project only exposes the data needed to detect that case). This includes the "completing a lesson in one track marks its `concept_id` siblings complete in other tracks" behavior described below — the data model supports it, but no progress table or completion UI exists yet in this sub-project.
- TTS audio synthesis (Listening/Speaking sub-projects) and AI-based grading (Writing/Speaking sub-projects) — lessons for these skills get full text content now, audio/grading capability is layered on later.
- **Deferred within this sub-project itself:** the `/admin/curriculum` merge UI (mark two or three cross-track lessons as the same concept, setting a shared `concept_id`) is designed for but not built. Until it exists, every lesson's `concept_id` is `null` — nothing is linked yet. `curricula/overlap-review.md` documents ~90 candidate concept groups found by manually diffing all 15 source files, as a reference for whoever builds/uses that UI; it does not get consumed automatically by anything.

## Authentication Addendum

Core shipped with no authentication ("local-only, single-user, no auth system"). This sub-project is the first to need a gated route (the admin browse UI), so it adds a small, scoped addendum to Core: simple password auth only (Google SSO deferred to a future public/multi-user phase — disproportionate OAuth setup for gating one local admin tool today). Implemented as an early task in this sub-project's plan, before the admin UI task.

- **Storage:** a new `admin_auth` table (`password_hash`, `created_at`). Password hashed with Node's built-in `crypto.scrypt` — no new dependency, consistent with how Core already handles crypto.
- **Sessions:** stateless, HMAC-signed HTTP-only cookie (signed with a server-side secret, following the same local-secret-file pattern as `lib/crypto/keyfile.ts`) — no session table, no cleanup job. Long-lived (e.g. 30 days, refreshed on activity), appropriate for a local single-user admin gate rather than a public system.
- **Gating mechanism:** NOT Next.js middleware — `middleware.ts` runs in the Edge Runtime, which lacks Node's `crypto` module, and introducing a second Edge-compatible crypto path just for this would be inconsistent with Core's existing Node-crypto-only approach. Instead, a shared `requireAdminSession()` check (in a new `lib/services/adminAuthService.ts`) is called at the top of each `/admin/*` page and each `/api/admin/*` route handler — the same per-route gating pattern Core's `app/page.tsx` already uses for the onboarding-completion redirect.
- **Flow:** visiting `/admin` with no `admin_auth` row yet shows a one-time "set admin password" form; once set, all `/admin/*` pages and `/api/admin/*` routes require a valid session cookie, redirecting to `/admin/login` otherwise.
- **Recovery:** if the password is forgotten, delete the `admin_auth` row directly (the developer already has full local DB access) — no email/SSO recovery flow needed at this scope.
- **Files:** `lib/services/adminAuthService.ts` (hash/verify password, sign/verify session cookie, `requireAdminSession()`), `app/api/admin/auth/route.ts` (setup/login/logout), `app/admin/login/page.tsx`.

Note: **only the `/admin/*` pages are gated.** The read-only curriculum data routes (see API Routes below) live under `/api/curriculum/*`, not `/api/admin/*`, and are intentionally ungated — sub-project #3 needs to call them for regular end-user features later, not just the admin browse UI. The admin UI is just one more consumer of that same public data API.

## Data Model (new SQLite tables, extending Core's DB)

- **`milestones`** — `id (stable slug), track, level, title, description, order_index`.
- **`sections`** — `id (stable slug), milestone_id, title, description, order_index`.
- **`lessons`** — `id (stable slug, level-namespaced — e.g. "b1-telc-reading-teil3-classifieds-matching"; a bare slug is only unique within its own source YAML file, and three slugs across the real files turned out to be reused for a genuinely different lesson at a different level of the same track, so the DB id prefixes the level to guarantee global uniqueness), track (generic|telc|goethe), concept_id (nullable, see below), source_level, skill (grammar|vocabulary|reading|listening|writing|speaking), title, explanation, examples (JSON), created_at`. Every row is one track's own lesson — there is no canonical/shared lesson row referenced by multiple tracks.
- **`lesson_placements`** — `id, lesson_id, section_id, order_index, created_at`. Places a lesson into its (single) track's structure. `created_at` (on both this table and `lessons`) is what lets sub-project #3 detect exactly which lessons/placements are new since a user's last sync (`curriculum_meta.last_synced_at`) — without it, #3 would only know "something changed," not what.
- **`lesson_track_overrides`** — `id, lesson_id, track, explanation, examples`. **Deprecated, unused.** Kept in the schema (harmless empty table) rather than dropped, since removing it would mean editing/deleting the tests and code of the old generation pipeline that referenced it as well; not worth the churn for a table nothing writes to. Do not populate it in new code — a track's own lesson row already carries its own content.
- **`exercises`** — `id (stable slug, "<lessonId>__ex<index>"), lesson_id, track, type (multiple_choice|fill_blank|flashcard|free_text), content (JSON, shape per type — see below)`. `track` is redundant with the lesson's own track (kept for filtering convenience, not semantics) — every exercise belongs to exactly one lesson, which belongs to exactly one track.
- **`lesson_prerequisites`** — `lesson_id, prerequisite_lesson_id`. Track+level-local: a lesson's prerequisites are always other lessons in the same source YAML file (same track, same level) — see the authoring rules in `docs/curriculum-content-authoring-prompt.md`. Consumed by sub-project #3's gating/sequencing logic.
- **`curriculum_meta`** — `seed_version, last_synced_at`. Lets the app detect "curriculum content changed since I last synced," which sub-project #3 needs to implement the described update-catchup behavior (redirecting a user to complete a newly-inserted prerequisite before returning them to their prior position).

## Cross-Track Concept Linking

> **2026-09-22 — superseded.** The single nullable `lessons.concept_id` column described below turned out to be the wrong mechanism once real linking was designed: a lesson in one track can legitimately match *multiple* lessons in another track that aren't equivalent to each other (e.g. one track combines two concepts another track splits into separate lessons), which a single shared ID can't represent without falsely linking those separate lessons together. Replaced by a `lesson_concept_links` many-to-many pairwise table — see `docs/superpowers/specs/2026-09-22-curriculum-admin-management-design.md`, "Data Model Changes" and "Key Decisions Log." The completion-sharing *intent* described below (query-time check across everything a lesson links to, no forced navigation) still holds; only the storage mechanism changed.

Core's spec promised mastery sharing across tracks for the same underlying concept. The original design achieved this by having one canonical `lessons` row referenced by every track that taught it (via `lesson_placements`), with `lesson_track_overrides` patching per-track differences. In practice, real content for the three tracks was authored **independently and richly** per track (see `curricula/*.yaml`) — the same grammar point often gets a differently-structured lesson, different examples, a different exercise mix, and sometimes different sub-scoping per track (see `curricula/overlap-review.md` for ~90 cataloged examples). Reconciling that into one shared lesson would mean picking a winner and discarding the other tracks' content for no real benefit.

Instead: **every lesson stays fully independent**, and cross-track equivalence is expressed with a lightweight, nullable `concept_id` on `lessons`. Lessons in different tracks that cover "the same concept" get the same `concept_id` string; a lesson with no cross-track equivalent has `concept_id = NULL`. This is set by an admin curator, not inferred automatically or at import time — the import always sets `concept_id = NULL`.

How this is meant to be used later (by sub-project #3, not built here):
- A lesson's completion status is read as "is there a completed record for this lesson, **or** for any other lesson sharing its `concept_id`" — a query-time check, not a write that fans out to every sibling lesson when one is completed. Completing "Personal Pronouns" in the Generic track would make Goethe's differently-worded equivalent show as already finished too, without touching Goethe's own row.
- It is the user's choice whether to also visit the sibling lesson in another track (e.g. after switching their active track in Settings) to see its explanation/exercises — nothing forces or blocks that; `concept_id` only affects completion status, never content or navigation.

**Setting `concept_id` (future work, not built in this sub-project):** the plan is an interactive merge action in the `/admin/curriculum` browse UI — an admin picks two or three lessons (one per track) they judge to be the same concept and the UI assigns them a shared `concept_id`. `curricula/overlap-review.md` (built by systematically diffing all 15 source files, three passes) is a candidate list for that UI to work from, not something consumed automatically.

**Exercise content JSON shapes:**
- `multiple_choice`: `{ question, options: string[], correctIndex }`
- `fill_blank`: `{ textWithBlank, correctAnswer, acceptableVariants?: string[] }`
- `flashcard`: `{ front, back }`
- `free_text`: `{ prompt, modelAnswer }`

Stable, slug-style IDs (not raw auto-increment integers) are used for `milestones`, `sections`, `lessons`, and `exercises` — for lessons specifically because mastery records and prerequisite edges key off lesson ID; for exercises because sub-project #3's future spaced-repetition tracking will key per-user item history off exercise ID, and a content update that silently reassigned IDs would break "has this user already seen this exact item" tracking. A future re-authoring pass that meaningfully changes an existing exercise's content should mint a new stable ID rather than mutate the old one in place, so any history already recorded against the old ID stays valid and the item is treated as new.

## Content Authoring & Import Pipeline

**This replaces the original three-phase AI-generation pipeline** (`scripts/generate-curriculum.ts` + `lib/curriculum-gen/{aiClient,phase1MasterPool,phase2TrackStructure,phase3Content,exportSeed,validate}.ts`), which has been deleted from the codebase. That pipeline was built and run for a pilot A1 scope; the self-generated content wasn't good enough (see Key Decisions Log), and the user instead hand-produced (via prompting other LLMs directly, outside this app) real, richly-detailed content for all 15 track×level combinations. Content authoring now happens **outside this codebase**, and this sub-project's job shrinks to importing it well:

1. **Authoring** — a human (or an LLM directed by a human, outside this app) writes one YAML file per track × level (`curricula/generic_A1.yaml` ... `curricula/telc_C1.yaml`, `curricula/goethe_C1.yaml` — 15 files), following the format specified in `docs/curriculum-content-authoring-prompt.md`: a flat, track-agnostic list of lessons for that level only, each with `slug`, `skill`, `title`, `prerequisites` (slugs within the same file only), `explanation`, `examples`, `exercises`. No milestone/section/track structuring happens in this step — that's deliberately left flat, see step 2.
2. **Import** — `scripts/build-curriculum-seed.ts` (`npm run build-curriculum-seed`) reads all 15 YAML files and converts each into the seed JSON format `loadSeedIfNeeded` consumes (one file per track+level in `data/curriculum-seed/`). For each file: every lesson becomes its own independent row (`track` set, `concept_id: null`), namespaced by level to guarantee a globally-unique DB id (see Data Model). Lessons are grouped into one milestone per skill (fixed order: grammar, vocabulary, reading, listening, writing, speaking) with a single section each, preserving the lesson's position within its YAML file — this is placeholder structure, not a pedagogically curated Milestone → Section tree; refining it is future admin-UI work, same as concept linking (see "Cross-Track Concept Linking" above). Exercises and same-file prerequisites are carried through directly.
3. **Loading** — unchanged from the original design: `loadSeedIfNeeded` (app side) is a merge/upsert, not a one-time "if empty, load." On every app start, it compares `curriculum_meta.seed_version` against the bundled seed files' version (all per-track-level files share one version number, bumped together); if newer, it upserts changed/added rows across all seed files by stable ID and updates `curriculum_meta`. This never touches a user's own progress data (Core's `memory_store`, profile, track/level settings), which lives in separate tables.

**Practical requirements (import path):**
- The converter is idempotent and safe to re-run: it wipes and rewrites `data/curriculum-seed/` from the current `curricula/*.yaml` files every time, rather than upserting — the YAML files are the source of truth, not the generated seed JSON.
- Bumping `SEED_VERSION` in `scripts/build-curriculum-seed.ts` is how a content update actually reaches a running app; the loader no-ops if the bundled version matches what's already loaded.
- No automated content-quality grading (same as the original design) — quality review happens by reading the YAML directly and via the admin browse UI once content is imported.
- **Known source-data quirk, worth knowing if re-importing:** a bare lesson `slug` is only guaranteed unique within its own YAML file. Three slugs across the real 15 files are reused for a genuinely different lesson at a different level of the same track (e.g. `telc-reading-teil3-classifieds-matching` is a real, distinct lesson at both A2 and B1) — the level-namespaced DB id (see Data Model) exists specifically to handle this without silent data loss on import.

## API Routes (read-only)

Under `/api/curriculum/*` — ungated (see Authentication Addendum above), following Core's established pattern (thin routes wrapping a service layer, server-side DB access only):
- List tracks/levels.
- Get a track's Milestone → Section → Lesson structure (for a given level, or the whole track).
- Get a lesson's content (explanation, examples, resolved against any track-specific override) and its exercise corpus (track-specific exercises falling back to shared ones).

These are the full interface sub-project #3 needs to query curriculum data — it builds no query layer of its own for this. The admin browse UI below is just one more consumer of these same routes.

## Admin Browse UI

A small, admin-only section (`/admin/curriculum`) for QA-ing the imported content: browse tracks → levels → milestones → sections → lessons, read full lesson content and its exercise corpus, by calling the same `/api/curriculum/*` routes any other consumer would. Gated by `requireAdminSession()` (see Authentication Addendum above). Exists purely for manual review — no automated content-quality grading.

**Built today:** browse-only (`app/admin/curriculum/page.tsx` → `[track]/[level]/page.tsx` → `lesson/[id]/page.tsx`), read-only, no mutations.

**Not yet built — the merge action:** picking two or three lessons (one per track, same underlying concept) and assigning them a shared `concept_id` (see "Cross-Track Concept Linking" above). `curricula/overlap-review.md` is the reference list a curator would work from. This needs, at minimum: a way to select lessons across tracks/levels for comparison, a write path (`PATCH`/`POST` under `/api/admin/curriculum/*`, gated like the rest of `/admin/*`) to set `concept_id`, and an undo/unmerge path. Scoping and building this is future work, not covered further by this spec revision.

## Testing Approach

- **Schema/migrations**: unit tests verifying the new tables, following Core's `lib/db/client.test.ts` pattern, plus a migration test covering the legacy-schema-drop path (an app.db created under the old shared-lesson schema must end up with the new `lessons.track`/`concept_id` columns and empty curriculum tables, without touching `profile`/`provider_connections`/etc.).
- **Query/service layer**: unit tests against an in-memory DB with small fixture data — hierarchy traversal, returning a lesson's own `track`/`concept_id`, prerequisite lookups. (Track-override fallback and exercise track-fallback no longer exist — every lesson/exercise belongs to exactly one track already, so `getLesson`/`getExercises` just look up by id.)
- **API routes**: integration tests hitting route handlers directly with a fixture-seeded temp DB, following Core's established pattern.
- **Content authoring**: no automated test — this now happens outside the codebase (see Content Authoring & Import Pipeline). Structural correctness of the *converter* (below) is what's tested, not the authored content's pedagogical quality.
- **YAML → seed converter** (`scripts/build-curriculum-seed.ts`): not yet unit-tested (deferred — flag for follow-up); correctness was instead verified by running it against the real 15-file `curricula/` corpus and checking, end-to-end: zero lesson-id collisions across all 303 imported lessons, zero dangling prerequisite references, `npm run build` succeeding, and the real dev DB serving the expected lesson/milestone/exercise counts via the running app's API routes.
- **Seed loader/merge logic**: unit tests verifying upsert-by-stable-ID behavior — new lessons inserted correctly into existing track order, changed content updated, a user's separate progress data left untouched, and that lessons sharing a `concept_id` load correctly without ever touching the (deprecated) `lesson_track_overrides` table.
- **Admin UI**: component tests following Core's established pattern (RTL, mocked fetch).
- **`adminAuthService`**: unit tests for password hashing/verification (real `crypto.scrypt` round-trip, following the rigor of Core's `lib/crypto/encrypt.test.ts`) and session cookie signing/verification (valid signature accepted, tampered/expired cookie rejected).
- **Admin auth routes/gating**: integration tests for the setup-then-login flow, and that `requireAdminSession()` actually blocks an unauthenticated request to a protected `/admin/*` page or `/api/admin/*` route.
- **Manual verification**: after import, spot-checked lesson/milestone/exercise counts and a sample lesson's content via the running dev server's API and the admin browse UI's auth gating.

## Key Decisions Log

Decisions from the original (AI-generation) design, still accurate:

- Each track has its own independent Milestone/Section structure and ordering.
- Milestone tests are **not** pre-composed or stored by this sub-project — only the per-lesson exercise corpus is pre-built; #3's algorithm assembles a mixed test from it at request time.
- Text-only content is built now for all six skill tags, including listening/speaking/writing, even though audio synthesis and AI grading aren't built until their respective later sub-projects — avoids having to backfill curriculum content later.
- Stable, slug-style IDs (not auto-increment integers) for milestones/sections/lessons, specifically to support safe content updates after initial ship without corrupting stored mastery/prerequisite references.
- Authentication addendum: password-only for v1 (Google SSO deferred to a future public/multi-user phase); Node's built-in `crypto.scrypt` and a stateless HMAC-signed session cookie, no new dependency and no sessions table; gated via a per-route `requireAdminSession()` check rather than Next.js middleware, since middleware runs in the Edge Runtime and lacks Node's `crypto` module — this keeps auth on the same Node-crypto approach Core already uses everywhere else.
- Curriculum data routes (`/api/curriculum/*`) are deliberately ungated and separate from `/api/admin/*` — sub-project #3 needs them for regular end-user features later, not just the admin browse UI, which is just one more consumer of the same routes.
- `lessons` and `lesson_placements` carry `created_at`, so sub-project #3 can diff against `curriculum_meta.last_synced_at` to know exactly which lessons/placements are new after a content update, not just that something changed.
- Seed data ships as one file per track+level, not a single monolithic file — keeps partial content updates reviewable and diffable at the scale this curriculum is expected to reach.

**2026-09-22 — the architecture pivot** (superseding the entries below them):

- The original design generated content once via an in-app AI pipeline (`scripts/generate-curriculum.ts`, three phases: master concept pool → track structuring → content generation), with `Concept = Lesson, 1:1` shared across tracks via `lesson_placements` and patched per-track via `lesson_track_overrides`. That pipeline was fully built and run for an A1 pilot; the user reviewed the self-generated content and rejected it ("I don't like the content you generated for A1"), then hand-produced real content for all 15 track×level combinations by prompting external LLMs directly (see `docs/curriculum-content-authoring-prompt.md`) and hand-editing/reviewing the result.
- Reading all 15 real files showed **zero slug overlap** between tracks (each was authored fully independently) but substantial *conceptual* overlap once compared closely (~90 candidate matches cataloged in `curricula/overlap-review.md` across three review passes) — confirming the "shared canonical lesson" model was a reasonable idea but the wrong mechanism for content this independently rich: merging would mean discarding two of three tracks' worth of examples/exercises for every matched concept, for a benefit (avoiding content duplication) that doesn't matter much at this scale.
- Decision: **every lesson is imported fully independently per track** (own id, own explanation/examples/exercises); cross-track equivalence is expressed only as a lightweight `concept_id` tag, to be set later by an admin via a not-yet-built `/admin/curriculum` merge UI, not inferred or merged automatically. See "Cross-Track Concept Linking" above.
- The AI-generation pipeline (`lib/curriculum-gen/*`, `scripts/generate-curriculum.ts`) was deleted rather than kept alongside the new import path — it wasn't referenced by any live app code, and keeping it would have meant either breaking its tests (it inserted into `lessons` without the new required `track` column) or weakening the new schema (making `track` nullable) to accommodate dead code.
- `lesson_track_overrides` was kept in the schema (rather than also removed) purely to avoid touching the old pipeline's remaining test files for a table that costs nothing to leave empty; it is not populated by anything going forward.
- Granularity is no longer AI-determined at generation time (there is no generation time); milestone/section structure is a deliberately flat placeholder (one milestone per skill) assigned at import, left for future admin curation — same deferred status as concept linking.
- TELC/Goethe structuring no longer relies on an AI's training-data knowledge of these exams — the real files were authored/reviewed by a human against the actual exam formats, which is a stronger accuracy guarantee than the original design's "no reference documents, trust the model's training knowledge" approach.
